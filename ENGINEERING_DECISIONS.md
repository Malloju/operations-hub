# Engineering Decisions

## 1. Data model and indexes
Collections: `users` (global role + `teamIds`), `teams`, `workitems`, `activities`, `idempotencykeys`, `counters`.
- **Work items are one document with a `version`** and a human key (`WI-1042`, from an atomic counter). References (reporter/assignee/team) are by id and populated on read; nothing is embedded that grows unbounded.
- **History is a separate, append-only `activities` collection** (comments are activity rows with `action: "comment"`). The history grows without bound, so it must not live inside the item; it is read paginated by `{item, createdAt}`. Each row stores actor, action, before/after, timestamp.
- `priorityRank` (1–4) is denormalised next to `priority` so "sort by priority" is an index sort rather than a string collation.
- **Indexes** follow the real queries: `{team,status,priorityRank,updatedAt}` (team-scoped lists/dashboard), `{assignee,status,updatedAt}` ("mine"), `{status,dueDate}` (overdue), `{updatedAt}`/`{createdAt}` (sorts), unique `key`, a `$text` index on title+description, `{item,createdAt}` on activity, unique `{userId,key}` + 24h TTL on idempotency keys. All list queries add `_id` as a sort tie-breaker so pages are stable.
- *Trade-off:* the counter document is a write hotspot for creation (fine at thousands of creates/day; would shard or use ULIDs at higher volume). Users hold `teamIds` on the user doc, so membership is a single read at auth time but there is no per-team role.

## 2. Authentication and authorization
- Login creates a **server-side session row** (TTL 8h) and issues a JWT carrying its id in an **httpOnly, SameSite=Lax cookie**, so XSS cannot read it. Logout deletes that row, so a copied token dies immediately while the user's other devices keep working; deactivation or a role/team/password change by an admin deletes all of the user's sessions. (An audit found a pure-stateless JWT stayed valid after logout; a first fix using a per-user counter signed users out of *all* devices, hence per-session rows.) Unknown-email logins still run a bcrypt compare so timing does not reveal which emails exist, and responses carry `nosniff`/`X-Frame-Options`/`no-store`/CSP headers. `JWT_SECRET` has no default; mutations must be `application/json`, which blocks simple cross-site form posts (CSRF defence in depth). Passwords are bcrypt-hashed. Secrets come from env.
- **The user and session are loaded from the DB on every request**, so deactivation, revocation and role/team changes apply immediately instead of after token expiry. Cost: two indexed reads per request (acceptable; cacheable later).
- Authorization is enforced **per resource on the server**: team scoping is baked into every list/aggregate query (`teamScope`), and single-item routes re-check membership (`loadAccessible`). Other teams' items are **404**, so existence isn't leaked. Client-supplied reporter/role/status/version-on-create are ignored/rejected (strict Zod schemas). Assignees must be active members of the item's team. The matrix is in the README.
- Admins manage teams/users through API endpoints (no UI). *Trade-off:* role is global plus team membership, rather than a per-team role table. Simple and sufficient to demonstrate the model; per-team roles would be the first extension.

## 3. Concurrent updates — optimistic concurrency
Every item has `version`. Edits send the version they read. Inside the transaction we (a) compare, and (b) write with a compare-and-set `findOneAndUpdate({_id, version}, {$inc: {version: 1}})`. Step (b) matters: it is what makes two truly simultaneous writers safe, not just sequential stale ones. The loser gets **409 `VERSION_CONFLICT`** with the current item in `error.details.current`. The UI shows a banner ("changed while you were viewing it – your change was not applied"), and loads the latest on request; **it never silently overwrites and never shows optimistic state** — the UI updates only from the server's confirmed response, which removes the need for rollback logic. The same mechanism resolves "two users claiming the same item": exactly one claim wins (tested with parallel requests).
*Trade-off:* a whole-document version means unrelated field edits also conflict (e.g. two people editing different fields). I chose correctness and simplicity over field-level merging. Comments don't bump the version because they are append-only and cannot conflict.

## 4. Idempotency / duplicate prevention
`POST /work-items` and `POST /work-items/:id/assign` require an `Idempotency-Key`. The key record (unique on `{userId,key}`) is inserted **in the same transaction** as the business write and stores the response. Outcomes:
- Retry after success → the stored response is replayed (`Idempotent-Replay: true`), no new item and no second audit row.
- Two identical requests at once → one commits; the other hits a write conflict/duplicate key and then replays (or gets 409 `REQUEST_IN_PROGRESS` if it still can't see the result).
- Same key, different body → 422 (a client bug, not a retry).
- A request that fails rolls back with its key, so the client can safely retry with the same key.
The client generates one key per create form instance, so a timeout-then-resubmit cannot duplicate. Disabling the button is only UX. Keys expire after 24h (TTL).

## 5. Audit consistency, async, testing, and what I left out
- **Atomicity:** each important mutation (create, patch, assign) writes the item, the audit rows and (if applicable) the idempotency record in **one MongoDB transaction**; if the audit write fails the update rolls back (tested by injecting a failure), and rejected requests (409/403/422) leave no audit rows. This needs a replica set (documented; a single-node replica set suffices). `USE_TRANSACTIONS=false` exists for standalone dev mongod but is explicitly *not* atomic. Comments are single-document inserts and need no transaction.
- **I intentionally did not build async processing.** The brief makes it optional; notifications/enrichment would need an outbox (write an event in the same transaction, a worker delivers at-least-once, consumers dedupe by event id). I'd rather ship fewer features with verified behaviour. The audit rows are structured so they could become that outbox.
- **Testing strategy** targets what is dangerous: stale/concurrent writes and claim races (parallel requests), idempotent retries incl. 8 simultaneous duplicates, 403/404/422 negatives for cross-team and role violations, workflow transitions, audit/rollback consistency, pagination without overlap, team-scoped search/dashboard. Tests hit a real MongoDB replica set, not mocks (the only mock is injected failure to prove rollback). Three layers: 30 API integration tests, 45 live black-box checks (`npm run e2e`: parallel races over real HTTP, input hardening, persistence), and 2 UI tests that drive the real React app against the live API, including the 409 conflict banner. A post-build audit of this suite found and fixed: sessions surviving logout, impossible dates causing 500s, an email-enumeration timing leak, missing security headers, a hardcoded fallback JWT secret, and unmapped DB-down errors.
- **Scale notes:** nothing loads the dataset in the browser or the API; list endpoints cap `pageSize` at 100; counts are index-backed. Next steps for growth: cursor pagination, cached dashboard aggregates, Atlas Search for fuzzy search, outbox + worker, archiving old activity.
